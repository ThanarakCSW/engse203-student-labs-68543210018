# ทางเลือกฐานข้อมูล — SQLite, NoSQL และ async

> บันทึกตอบคำถามจากบท "อ่านเพิ่มเติม" (CP41)
> รายวิชา ENGSE203 การพัฒนาเว็บแอปพลิเคชัน

## 1. ทำไมโปรเจกต์นี้เลือก SQLite แทน MongoDB

ข้อมูลของระบบ Campus Service (ประกอบด้วย users และ requests) **มีโครงสร้างที่ชัดเจนและมีความสัมพันธ์กันอย่างแน่นอน** — คำร้องแต่ละใบจะต้องระบุผู้ยื่นคำร้องผ่าน foreign key ที่เชื่อมโยงไปยังตารางผู้ใช้งาน

SQL และ Relational Database มีความเหมาะสมกับข้อมูลลักษณะนี้ด้วยเหตุผลสำคัญ:
- **บังคับใช้โครงสร้างและเงื่อนไข (Schema & Constraints):** สามารถกำหนด `NOT NULL`, `CHECK`, `FOREIGN KEY` และ `UNIQUE` เพื่อป้องกันข้อมูลขยะหรือข้อมูลที่ไม่สมบูรณ์ตั้งแต่ระดับฐานข้อมูล
- **การเชื่อมโยงข้อมูล (JOIN):** สามารถดึงข้อมูลคำร้องพร้อมข้อมูลชื่อ แผนก และอีเมลของผู้ยื่นคำร้องได้ใน SQL Query เพียงคำสั่งเดียวอย่างมีประสิทธิภาพ
- **ความสัมพันธ์ระหว่างตารางเป็นแกนหลัก:** การออกแบบฐานข้อมูลเชิงสัมพันธ์ทำให้การเก็บข้อมูลเป็นระเบียบตามหลัก Normalization ไม่เกิดข้อมูลซ้ำซ้อน

ในขณะที่ **MongoDB (NoSQL Document Store)** จะเหมาะสมกว่าเมื่อข้อมูล**ไม่มีโครงสร้างตายตัว (Unstructured / Semi-structured)** หรือแต่ละรายการมีฟิลด์ข้อมูลที่แตกต่างกันอย่างสิ้นเชิง เช่น ระบบบันทึก Log เหตุการณ์, ระบบจัดเก็บเอกสารหลากหลายฟอร์ม หรือข้อมูล Sensor จากอุปกรณ์ IoT

## 2. หากในอนาคตจำเป็นต้องเปลี่ยนไปใช้ MongoDB จะส่งผลกระทบต่อชั้นใดบ้าง

| ชั้นของสถาปัตยกรรม | ส่งผลกระทบหรือไม่ | เหตุผลประกอบ |
|---|---|---|
| **Presentation Tier (Frontend)** | ไม่ได้รับผลกระทบ | ฝั่งหน้าบ้านยังคงเรียกใช้งาน HTTP API เส้นทางเดิม และรับข้อมูล JSON โครงสร้างเดิม โดยไม่จำเป็นต้องรับรู้ว่าฐานข้อมูลเบื้องหลังคืออะไร |
| **Application Tier (Controller)** | ได้รับผลกระทบ | ต้องปรับเปลี่ยนการเรียกฟังก์ชันใน Service ให้รองรับ `async/await` เนื่องจาก MongoDB Driver ใน Node.js ทำงานแบบ Asynchronous ข้ามเครือข่ายทั้งหมด |
| **Application Tier (Service)** | ได้รับผลกระทบเต็มที่ | ต้องเขียนโค้ดใหม่ทั้งหมด โดยเปลี่ยนจากคำสั่ง SQL ของ better-sqlite3 ไปใช้คำสั่งของ Mongoose หรือ MongoDB Node Driver แทน |
| **Data Tier (Database)** | เปลี่ยนแปลงทั้งหมด | ย้ายจากไฟล์ `campus.db` ไปยัง MongoDB Database Server (เช่น MongoDB Atlas) |

> **ข้อสังเกต:** การเปลี่ยนแปลงครั้งนี้ต่างจากการเปลี่ยน Service 4 ครั้งก่อนหน้านี้ในรายวิชา เพราะครั้งนี้เป็นการเปลี่ยนจาก Synchronous (SQLite ไฟล์ในเครื่อง) ไปเป็น Asynchronous (MongoDB ข้ามระบบเครือข่าย) ซึ่งเป็นการเปลี่ยน Method Signature ของ Service Layer จึงส่งผลกระทบต่อเนื่องมายัง Controller ด้วย

## 3. การประมวลผลแบบ async มีความจำเป็นในกรณีใด และไม่จำเป็นในกรณีใด

| สถานการณ์การทำงาน | ต้องรอคอยทรัพยากรหรือไม่ | ควรใช้ async หรือไม่ |
|---|---|---|
| **SQLite (ไฟล์ฐานข้อมูลในเครื่องเดียวกัน)** | อ่านและเขียนเสร็จสิ้นทันทีใน memory/local disk | ไม่จำเป็นต้องใช้ |
| **MongoDB Atlas (ฐานข้อมูลบน Cloud ต่างเครื่อง)** | ต้องรอคอยการส่งข้อมูลไป-กลับผ่านเครือข่าย (Network Latency) | จำเป็นต้องใช้ `async/await` |
| **การเรียกใช้งาน External API (Third-party Service)** | ต้องรอการตอบสนองจากเซิร์ฟเวอร์ภายนอก | จำเป็นต้องใช้ `async/await` |
| **การอ่านไฟล์ขนาดใหญ่จากดิสก์ (Large File I/O)** | ต้องรอรอบการหมุนและหัวอ่านของ Disk I/O | ควรใช้ Stream หรือ async |

**หลักการพิจารณา:** ควรเลือกใช้ `async/await` เมื่อขั้นตอนการทำงานนั้นเกี่ยวข้องกับ **I/O Bound (เครือข่าย, การเชื่อมต่อภายนอก หรือดิสก์ที่ใช้เวลานาน)** เพื่อป้องกันไม่ให้ JavaScript Main Thread เกิดการบล็อกการทำงาน (Non-blocking I/O) ทำให้เซิร์ฟเวอร์สามารถรองรับคำขออื่นๆ ต่อไปได้พร้อมกัน
